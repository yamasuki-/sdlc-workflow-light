# 工程内の共通フロー（全工程が同じ型）

```
計画 → 作成 → レビュー → 完了判定（ゲート）
plan    work    review     gate
```

各工程スキル（`phase-*`）はこの型に従い、工程固有の内容（入力・成果物・作業・完了条件）だけを定める。
現在のステップは `state/phase.json` の `step` に記録し、ステップを移るたびに
`scripts/sdlc phase step <step>` を実行する。中断後は記録されたステップから再開する。

`<P>` は工程 ID（例 `02-design`）を表す。

---

## 0. 開始・再開

1. `scripts/sdlc status` を実行し、`現在工程 == <P>` であることと、再開ステップを確認する。
2. `scripts/sdlc gate check <P>` で、前の人間ゲートが有効か確認する（無効なら停止して人に報告）。
3. 前の人間ゲートの記録 `state/gates/<工程>.md` があれば **Read ツールで**読み、**条件付き承認の条件**・コメントを把握する。
   条件は本工程の計画に必ず反映する。
4. 割り込み対応中（`モード: 不具合対応 / 変更要求対応`）なら「差分やり直し」（末尾）を併せて適用する。
   人間ゲートが差戻し（`revise`）なら「差戻し対応」（末尾）を適用する。

## 1. 計画（plan）

- 入力: 前工程までの成果物、人間ゲートのコメント・条件、`state/decisions.md`・`state/open-questions.md`、`rules/`。
- `docs/<P>/plan.md` をテンプレート `<SDLC>/templates/plan.md` から作る。短くてよい:
  作業範囲（対象 ID）、成果物ファイル、**作業単位と担当ファイル**（並行させるなら重ならないように）、前工程の条件への対応、リスク。
- 完了したら `scripts/sdlc phase step work`。

## 2. 作成（work）

- 工程スキルが指定するエージェントに、作業単位ごとに依頼する。**並行は最大 2**（担当ファイルが重ならない単位だけ。
  1 つのメッセージの中で Agent ツールを 2 回呼ぶ）。小さい工程はエージェント 1 体で順に進めてよい。
  - コードを並行して書く場合は `isolation: "worktree"` を使い、完了ごとにメインへ `git merge --no-ff` する。
- 依頼文は下の「作業指示テンプレート」で書く。
- 結果を受け取ったら確認する:
  - 担当ファイル以外を変更していないか（`git status` / `git diff --stat`）
  - 自己検証が「合格」か、トレース記法が守られているか
  - 報告の「決定事項」「未解決事項」は、**オーケストレータが**記録する:
    `scripts/sdlc decision add "<内容>" --source <作業単位>` /
    `scripts/sdlc question add "<内容>" --priority 高|中|低 --source <作業単位>`。
    優先度「高」（答えで成果物が大きく変わる）は、その場で人に確認する。
  - 不合格なら 1 回だけ指示を補って再実行し、再度失敗したら人に報告して停止する。
- 全体の整合を確認する: `scripts/sdlc trace check`、ID の重複・用語の揺れ、ファイル間の矛盾。
  コードを含む工程は `project.yaml` の `commands.test` / `lint` を実行する。
- **機械チェック**: `scripts/sdlc check` を実行する（`docs/<P>/checks.md` に記録される）。
  MUST が失敗（終了コード 4）なら直してから進む。同じ MUST が 3 回続けて失敗したら、環境・設定の問題の可能性があるので人に報告して停止する。
  未インストールで skipped のチェックは失敗扱いにしない（未解決事項に「CI で実行が必要」と記録する）。
- `docs/<P>/summary.md`（テンプレート `<SDLC>/templates/summary.md`）に成果物一覧・チェック結果を記録する。
- `git add -A && git commit -m "<P>: 作成"`。`scripts/sdlc phase step review`。

## 3. レビュー（review）

- **reviewer エージェント 1 体**に依頼する。作成者とは別コンテキストであること。工程スキルがレビュー不要とした工程は省く。
  - 渡すもの: 工程 ID、成果物パス、`<SDLC>/checklists/<P>.md`、上流の成果物、人間ゲートの条件、
    `docs/<P>/summary.md`、`docs/<P>/checks.md`
  - 出力先: `docs/<P>/review.md`（テンプレート `<SDLC>/templates/review.md`）
- 指摘があれば、**元の作成者と同じ種類のエージェント**に直させ（reviewer には直させない）、`scripts/sdlc check` を再実行して再レビューする。
  最大 2 往復。残った指摘は `review.md` の「残指摘」に理由付きで残す。
- `git add -A && git commit -m "<P>: レビュー完了"`。`scripts/sdlc phase step gate`。

## 4. 完了判定（gate）

`scripts/sdlc status` の `次のアクション` に従う。

- **人間ゲートのある工程**（01 と、`project.yaml` の `gates` に追加した工程）: 人に次を提示して**停止する**
  （自分で承認しない・次工程に進まない）。

  ```
  ## 工程 <P> の承認依頼
  - 成果物: <docs/<P>/ 以下の一覧>（`scripts/sdlc gate artifacts <P>`）
  - 人に見てほしい点: <仕様の要点・判断が必要なこと・仮定で進めた点>
  - レビュー結果: docs/<P>/review.md（判定・残指摘の要約）
  - 機械チェック: docs/<P>/checks.md
  - 決定事項 / 未解決事項: <今工程で追記したもの。優先度 高を先に>

  承認・差戻しは端末で次を実行してください（承認時に機械チェックを再実行します）:
    scripts/approve <P>
  承認後に /sdlc を実行すると次工程へ進みます。
  ```

- **人間ゲートの無い工程**: `scripts/sdlc phase advance` を実行する。機械チェックの MUST が通り、レビュー判定が不合格でなければ
  次工程へ進む（失敗したら理由に従って直す）。人への報告は工程の要約を数行で伝えるだけでよい。

---

## 差戻し対応（人間ゲートが「差戻し」の場合）

1. `state/gates/<P>.md` のコメント（修正指示）を Read で読む。
2. 指摘ごとに直す → 機械チェック → レビュー（差戻し指摘が解消したかを観点に追加）→ 完了判定。

## 差分やり直し（不具合・変更要求の対応中）

`<ID>` は不具合票 `state/defects/DEF-xxx.md` または変更要求票 `state/changes/CR-xxx.md`。

1. 票の内容（現象・原因・変更内容・SPEC/TC の差分）を読む。
2. `docs/<P>/plan.md` に「## <ID> 差分やり直し」節を追記する。**関係する ID・ファイルだけ**を対象にし、全面やり直しにしない。
   関係範囲は `scripts/sdlc trace impact <ID...>` で確かめる。新しい項目は既存 ID の続きで採番する。
3. 不具合では、同じ誤りを検出する自動テスト（結合テストか、ロジックなら単体テスト）を追加する。
   変更要求では、変更後の振る舞いを確かめる TC を 01 で追加・変更する。
4. レビューでは「原因が解消したか・変更どおりか」「関係範囲の外を変更していないか」を必ず確認する。

## 作業指示テンプレート

```
あなたは SDLC ワークフロー（軽量版）の <agent> として、作業「<title>」を担当する。
工程: <P>（<工程名>）
入力（読むもの）: <上流成果物のパス・ID>
担当ファイル（これ以外は変更禁止）: <files>
対象 ID: <ID>
既知の前提: <state/decisions.md の関連決定事項、ユーザの最近の指示など、ファイルに書かれていない補足>
プロジェクト固有ルール: rules/common.md, rules/<工程ID>.md（あれば従う）
作業内容: <工程スキルが定める作業>
テンプレート: <<SDLC>/templates/...>
完了条件: <工程スキルの自己検証項目>
禁止: state/ の変更、scripts/approve の実行、担当外ファイルの変更、承認済み成果物の変更、結果シートへの記入
スコープ: 指示された範囲を指示された粒度で完遂する。依頼が誤っている・より良い方法があると考える場合は
1 文で指摘したうえで指示どおり進める（黙って範囲を狭めたり広げたりしない）。成果物は内容に見合った長さにし、
前段の再掲や定型の結語で水増ししない。
（worktree の場合）作業の最後に担当ファイルを git add してコミットすること。
最後に「結果報告フォーマット」で報告すること。
```

## 結果報告フォーマット（全エージェント共通）

```
## 結果報告 <作業名>
- 状態: 完了 | 失敗 | 要確認
- 変更ファイル: <パス一覧>
- 作成・更新した ID: <ID 一覧>
- 自己検証: <完了条件ごとに 合格/不合格 と根拠>
- テストの変更: なし | <削除・期待値変更の内容と理由>
- 決定事項: なし | <作業中に決めたこと（オーケストレータが state/decisions.md に記録する）>
- 未解決事項: なし | <人の確認が必要なこと。優先度 高/中/低 を付ける（オーケストレータが state/open-questions.md に記録する）>
- 懸念: <あれば>
```
